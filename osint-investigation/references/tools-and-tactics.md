# Tools & Tactics (OSINT-specific)

Browser *mechanics* live in the `playwright-cli` skill. This file covers only the OSINT-specific tactics layered on top.

## Beating bot / login / CAPTCHA gates: attach to the user's real browser
Many high-value sources (state Secretary-of-State portals, LinkedIn, Joint Commission) sit behind Cloudflare, login, or CAPTCHA that a headless browser cannot pass. Tactic:
1. Ask the user to enable remote debugging in their own browser (Edge/Chrome: `edge://inspect` / `chrome://inspect` → "Allow remote debugging for this browser instance") with the relevant tab/login open.
2. Attach: `playwright-cli attach --cdp=msedge` (or `--cdp=chrome`). Requests now inherit the user's cookies and Cloudflare clearance.
3. The user solves any CAPTCHA / login; you navigate, read with `playwright-cli eval`, and screenshot.
4. **Target the right tab explicitly**, the user is browsing too, so list/select tabs rather than assuming "current."
5. Remind the user to turn remote debugging back off when done.

**When you do not need the user's logged-in profile** (public records behind a bot/Cloudflare wall, not a login): the bundled Playwright Chromium often gets a hard 403 *at the door* (observed on IDFPR, BBB, and the Georgia SoS portal), while a real Edge passes. Launch a dedicated, throwaway Edge so the user's own browser stays untouched, then attach to it:
```bash
msedge.exe --remote-debugging-port=9222 --user-data-dir="<temp>/edge-debug" --no-first-run --no-default-browser-check <url>
playwright-cli -s=<name> attach --cdp=http://localhost:9222
```
Drive and screenshot through that session; hand any CAPTCHA to the user in the visible window. Use `detach` (not `close`) when done so the external Edge keeps running for the user to close. Confirm the `msedge.exe` path and that `--remote-debugging-port` still works in the installed Edge before relying on this.
- Some portals expose an internal JSON API the page calls. From the user's cleared browser console, a `fetch(...)` to that endpoint returns structured data, far faster than clicking through the UI. The same `curl` from outside fails (no clearance; the clearance is IP-bound).
- **CAPTCHA is per-search on ASP.NET WebForms gov portals** (e.g. BotDetect): the form is POST-only + viewstate-validated, a plain GET returns 403, and the whole site blocks non-browser clients (curl 403). Each submit needs a fresh solve, and result "detail" links are often `__doPostBack` calls, not URLs. Run a **hand-off loop**: automation fills the fields, the user types the CAPTCHA and clicks submit, then you read/screenshot the result. Do not burn turns OCR-ing deliberately-distorted CAPTCHA images.
- **Look for a no-CAPTCHA bulk/report endpoint** before grinding per-record lookups. The same agency that gates individual lookups behind a CAPTCHA often publishes a separate "licensing reports" / bulk-list generator with no CAPTCHA (filter by board/category/county), one query returns the whole roster to search offline.

## Footprint discipline (don't tip off the subject)
Some "lookups" notify the subject. **Viewing a person's LinkedIn profile while logged in sends them a "X viewed your profile" notification**, from the user's own account, alerting the subject of the investigation. Prefer low-footprint public sources that answer the same question silently: the employer's own staff/provider directory, CMS NPI, Psychology Today / professional directories, news. Reserve a logged-in LinkedIn view for when the user accepts the footprint (or uses private mode). Flag the trade-off to the user before doing anything that leaves a trace on the subject.

## Rendered ≠ raw HTML (what a page actually shows)
`WebFetch` reads a page's raw HTML/markdown, so it can report names/content that the page **does not actually render** (placeholder/template debris left in the DOM, a collapsed/hidden slider, `opacity:0` animation that never fires). Do not assert "their site lists X" from a fetch alone. Confirm in a real browser: compare `document.body.innerText` (rendered) against `document.documentElement.innerHTML` (DOM); if a name is in the HTML but not the innerText, it is debris, not a presented claim. Also: the *real* content (e.g. the genuine staff roster) may live on a **different page** than the obvious one (`/meet-the-team/` vs a bare `/about-us/`), check sibling pages before concluding something is absent.

## Sub-agents for parallel deep dives
Spin up sub-agents for independent threads (one per person, entity, or registry). Brief each with: the due-diligence lens, facts-with-sources, confidence labeling, and explicitly **"report your findings back to me; do NOT write to the vault."** The main agent verifies and captures. Sub-agents cannot solve CAPTCHAs, hand those back to the user.

## Evidence capture
- Screenshot key records into the vault `Files/` folder and embed them in the relevant reference note (`![[name.png]]`). Name descriptively, e.g. `PA SoS - <Entity>.png`.
- **When the user pastes an image**, the harness saves it to an image-cache path and gives it to you; copy that file into `Files/` (`cp "<image-cache>/N.png" "<vault>/Files/<name>.png"`) and embed it. Do not rely on the chat copy.
- `playwright-cli screenshot --filename="<vault>/Files/<name>.png"`. Heavy pages (Facebook) may time out the screenshot, fall back to asking the user to capture it.
- **One proof note per entity × source, attached to the entity (principle 3).** Each captured record becomes its own atomic proof note holding the source URL, the embedded screenshot / PDF, and the extracted facts, titled for and linking to the entity it concerns, never bundled across subjects. Worked example (clinician license check): for each treating clinician, capture their FSMB DocInfo profile (board status + discipline) and CMS NPI record, embed both screenshots in a single per-person note `<Name> License Verification` that links `[[<Name>]]`; the person note then carries a **Verification** section linking that proof note; the investigation's Raw Log links the per-person notes and states only the synthesized verdict ("both treating psychiatrists hold active licenses with no board actions"). The same shape applies to a company filing (a per-entity Secretary-of-State or 990 proof note linked from the org), not a pooled "Records" note. Decompose, never bundle: if you find yourself putting two subjects' evidence in one note, split it.

## APIs & quick checks
- `curl -sSIL <url>` to inspect redirect chains, e.g. confirming a rebrand (old brand domain → new brand domain) or that an entity's site is live.
- **WHOIS / domain registration: use RDAP, not the registrar's web UI.** GoDaddy's WHOIS results page (and most registrar lookup pages) hard-block automated fetches with a 403, so do not burn the browser-handoff dance on them. RDAP is the modern, authoritative replacement: it returns structured JSON and is fetchable directly with WebFetch or curl, no key. For `.com` / `.net`, hit Verisign's registry: `https://rdap.verisign.com/com/v1/domain/<domain>`. For any other TLD, use the bootstrap `https://rdap.org/domain/<domain>`, which redirects to the right registry (WebFetch hands cross-host redirects back to you rather than following them, so just call the redirect URL it returns). Pull from the JSON: the `events` (registration / last-changed / expiration dates), `registrarName`, the nameservers' `ldhName`, the `status` codes, and the registrant `vcardArray` (usually redacted for privacy). This single record gives you **domain age** (tests a "founded in YYYY" claim against when the brand actually first registered its domain), the **registrar and nameserver host** (which DNS/email/host provider runs it), and **privacy-shield status**. When a subject has more than one domain, compare their creation dates: a shared registration day is a strong tell the domains were stood up together in one batch (e.g. Rize OC's `rizeoc.com` and `rizeocmentalhealth.com` were both first registered 2022-09-13, undercutting a "founded 2010" claim, even though one sat at GoDaddy and the other at Google Domains/Squarespace).
- Public JSON APIs are fetchable directly with WebFetch or curl, no key: CMS NPI Registry (`npiregistry.cms.hhs.gov/api/...`), Socrata open-data (e.g. `data.ny.gov/resource/<id>.json?$q=...`). OpenCorporates returns 401 without a token.
- **The Joint Commission Quality Check is a bot-blocked JS SPA, but the archived Quality Report PDF is server-generated and fetchable directly.** `apps.jointcommission.org/QualityCheckHistory/pdfgen.aspx?hcoid=<HCO_ID>&x=pdf&yr=<YEAR>&ver=1&hst=Y` downloads the authoritative accreditation report (decision, effective dates, certifications, the four patient-safety goals, and every location of care with its services). Get the HCO/Org ID from the provider-locator index first; navigating the URL in a browser triggers a file download. Verify the endpoint still resolves before relying on it; if it has changed, fall back to driving qualitycheck.org in a real browser (it blocks automation, so use the real-Edge-over-CDP method above).
